# snapfuzz

LLM-guided snapshot fuzzing for x86-64 binaries, no source needed. Windows PE and
Linux ELF. Built on [wtf](https://github.com/0vercl0k/wtf) as the execution engine
and Ghidra for static analysis.

Point it at an executable. It decompiles, has an LLM pick the fuzz entry and derive
the input format and harness, generates a C++ wtf module, takes a snapshot, fuzzes it
across a master and N workers, then dedups, replays and triages the crashes into a
GHSA advisory.

## Install

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m tools.bootstrap
```

`bootstrap` checks every tool, downloads Ghidra if it is missing, and writes the paths
into `config/`. `--check` reports without changing anything; `--vm-check` reports only
what snapshot acquisition needs.

Requires Python 3.11+, JDK 21+, a Visual Studio C++ toolchain, and an LLM provider key.

## Set an API key

Whichever provider's key you set is the one that runs. Put it in `.env`:

```
ANTHROPIC_API_KEY=sk-ant-...      # Claude, via the official SDK
OPENAI_API_KEY=sk-...             # OpenAI
SNAPFUZZ_LLM_API_KEY=sk-...       # any OpenAI-compatible endpoint
```

With more than one set, `config/llm.yaml` order decides. Pin one for a single command:

```powershell
$env:SNAPFUZZ_LLM_PROVIDER="anthropic"
```

## Build

```powershell
.\.venv\Scripts\python.exe -m fuzzer.build
```

## Run with an existing snapshot

`state/` already holds `mem.dmp` and `regs.json`:

```powershell
python -m orchestrator.pipeline `
    --binary targets\tlv_server\target\tlv_server.exe `
    --state-dir targets\tlv_server\state `
    --target-name snapfuzz --module snapfuzz `
    --workers 2 --minutes 15
```

`--entry-symbol` is optional; the LLM picks the entry in stage 03.

## Run on your own binary

You need the binary and a snapshot of it stopped at its parser. Put one seed — a single
input your target accepts, byte for byte — in `inputs/`; the other four per-target
directories are created for you.

```powershell
mkdir targets\mytarget\inputs
copy <one sample input> targets\mytarget\inputs\seed.bin

python -m orchestrator.pipeline `
    --binary C:\path\to\mytarget.exe `
    --state-dir targets\mytarget\state `
    --target-name mytarget `
    --workers 2 --minutes 15
```

Three things happen automatically that are worth knowing about:

- **The harness is generated from your binary.** Ghidra's pseudo-C goes to the model,
  which derives the input structure and the harness spec; `fuzzer/codegen.py` renders
  the C++ and stage 10 compiles it. The checked-in harness parses the development
  target's format, so for any other binary it is generated by default. Force either way
  with `--generated-harness` / `--handwritten-harness`.
- **The fuzz entry is chosen in stage 03**, not taken from `config/target.yaml`.
- **Artifacts are stamped with the target and the binary's hash.** Switching targets
  re-runs the analysis stages rather than reusing the previous target's, and prints
  which artifact it is re-running and why.

`--module` is wtf's `--name`, the harness compiled into `wtf.exe`. It is not your
target's module name — that comes from `--binary` — and not the target directory, which
is `--target-name`. The run header prints all three.

## Run from a binary — Windows

Needs Hyper-V, `kd.exe` from the Windows SDK,
[0vercl0k/snapshot](https://github.com/0vercl0k/snapshot), and a guest VM
([docs/GUEST-VM.md](docs/GUEST-VM.md)).

```powershell
python -m orchestrator.pipeline `
    --binary targets\tlv_server\target\tlv_server.exe `
    --state-dir targets\tlv_server\state `
    --target-name snapfuzz --module snapfuzz `
    --kd-pipe \.\pipe\snapfuzz `
    --kd-stimulus "python -m tools.poke_tcp --port 1337 --hex 00000000 3905 0200 0102" `
    --workers 2 --minutes 15
```

`--kd-pipe` adds the acquisition stage. Add `--wow64` for a 32-bit target.

## Run from a binary — Linux

Needs a Linux host with KVM. Build the guest once:

```bash
cd linux_mode/qemu_snapshot && ./setup.sh
```

Then:

```bash
python -m prep.snapshot_linux check-host

python -m prep.snapshot_linux prepare \
    --target-name mytarget --binary ./mytarget --break-at parse_packet \
    --stimulus '/root/mytarget &'
```

`prepare` writes the `bkpt.py` gdb sources, puts the ELF where `nm` and `readelf` will
read it, and prints the remaining steps — including one that cannot be automated:
mid-snapshot gdb asks you to press Ctrl+C in the QEMU tab and run `cpu`. `--dry-run`
shows the plan without touching anything.

When the three artifacts exist:

```bash
python -m prep.snapshot_linux verify --target-name mytarget

python -m prep.snapshot_linux ingest --state targets/mytarget/state \
    --module mytarget --module-base 0x555555554000 --ghidra-image-base 0x100000 \
    --entry-runtime-addr 0x5555555551a9 --randomize-va-space 0 \
    --out artifacts/a1_snapshot.json

python -m orchestrator.pipeline --binary ./mytarget \
    --state-dir targets/mytarget/state --target-name mytarget \
    --from 08 --workers 2 --minutes 15
```

Set `kernel.randomize_va_space=0` in the guest before snapshotting — ingest refuses
otherwise.

## Stages

```
01-pseudoc    Ghidra: decompile at module scope       -> A2
02-a2         A2 -> SQLite cache
03-entry      LLM: choose the fuzz entry              -> FuzzEntry
04-blocks     Ghidra: enumerate basic blocks          -> A3
05-covfile    A3 -> wtf .cov breakpoint file
06-datasyms   Ghidra: global data symbols             -> A6
07a-acquire   drive KD to take the snapshot           (only with --kd-pipe)
07-snapshot   ingest state/                           -> A1
08-inputspec  LLM: derive the input structure         -> InputSpec
08b-harness   LLM: derive breakpoints + input reg     -> HarnessSpec
09-codegen    InputSpec + HarnessSpec -> C++ (no LLM)
10-build      build wtf + the module
11-fuzz       campaign: master + workers + slow clock
12-analysis   dedup, classify, replay, trace (no LLM)
13-triage     LLM: five-signal triage                 -> advisory.md
```

Run one stage on its own: [docs/STAGES.md](docs/STAGES.md).

## Options

| Flag | Effect |
|---|---|
| `--list` | list the stages and exit |
| `--dry-run` | print the plan, run nothing |
| `--only 03 08` | run only these stages |
| `--from 10` | start here |
| `--force` | re-run stages that are up to date |
| `--scope function-closure` | narrow analysis to the entry's call closure |
| `--generated-harness` | derive and compile the harness from this binary's pseudo-C |
| `--handwritten-harness` | use the checked-in `fuzzer_snapfuzz.cc` instead |
| `--workers N` | worker count |
| `--minutes N` | campaign length |
| `--label NAME` | output directory under `artifacts/runs/`; defaults to the target name |
| `--kd-pipe`, `--kd-stimulus`, `--wow64` | Windows snapshot acquisition |

## Output

```
targets/<name>/outputs/                        minimised corpus
targets/<name>/crashes/                        raw crashes
targets/<name>/coverage/                       .cov breakpoint files
artifacts/a1_snapshot.json                     the snapshot reference
artifacts/runs/<label>-analysis/buckets.json   deduplicated crashes
artifacts/runs/<label>-triage/advisory.md      GHSA advisory, confirmed only
artifacts/runs/<label>-triage/discarded.jsonl  false positives, not shipped
```
