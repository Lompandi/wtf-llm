每個 target 一份獨立完整資訊，最後是三者放在一起看的結果。兩個是只給 binary 加 snapshot 的真實 target；第三個是 wtf 自己的範例，有原始碼可以對照答案。

概觀：三個 target 是三種形狀的問題

「輸入要滿足幾個條件」是解釋所有數字的那個變數。條件越少， 隨機 mutation 越容易撞到，引導能貢獻的空間越小。

fuzzing-test-cmp 的臂比較還在跑

它的端到端結果是完整的（7 個 bucket、7 個確認），但五臂比較尚未完成， 所以這一格是空的而不是 0。而且它的 baseline 臂可能跑不起來：選用內建 mutator 且有 client 驅動時，wtf 的 master 會以 0xC0000409 退出。這在 fuzzing-base-test 上 3 次全崩，在 tlv_server 上五臂都跑完，用手寫模組也會重現， 所以是 wtf 那邊的問題。

CWE-125 而不是 CWE-121，是因為讀先發生

fuzzing-test-cmp 的 memcpy(local_100, param_1, param_1[4]) count 來自輸入，所以複製會先跑過來源緩衝區的尾端，才有機會蓋掉 224 bytes 的目的地。讓那個讀取真的 fault 的是 page-tail 擺放——輸入貼著未映射頁 的邊界放。越界讀是 DoS，不是 RCE，triage 的分類是對的。

這些數字不能說明什麼

每臂各跑一次、五分鐘——足以分開 4 個 bucket 和 1 個，不足以給信賴區間。 fuzzing-base-test 的 baseline-libfuzzer 缺執行次數，因為 master 的 stdout 緩衝未 flush（D-033）；corpus 與 bucket 來自檔案系統，不受影響。 三個 snapshot 都是既有的，不是在這裡取得的，所以 snapshot 取得那條路徑仍未被執行過。
